📖 What is IDOR?

Fundamentals

Insecure Direct Object Reference (IDOR) is an access control vulnerability that occurs when an application uses user-supplied input to directly access objects — such as database records, files, or API resources — without verifying that the authenticated user is authorized to access that specific object.

The Core Problem in One Sentence

The application checks "Is someone logged in?" (Authentication ✅) but never checks "Is THIS person allowed to access THIS specific resource?" (Authorization ❌)

🏨 The Hotel Analogy

1

🔑 Key Card

You check into a hotel and receive a key card. This is authentication — the hotel knows WHO you are.

2

🚪 Your Room

Your key card should ONLY open Room 301 — YOUR room. This is authorization — controlling WHAT you can access.

3

🔓 The Bug

You type "302" on the keypad and it opens Room 302! The system never verified your card was authorized for that room.

4

💥 Impact

You can now enter ANY room simply by guessing the number. Every guest's belongings, privacy, and safety are compromised.

🔐 Authentication vs Authorization — The Critical Difference

🔑 Authentication (AuthN) WHO are you?

"Prove your identity"

  • Username & Password verification
  • Session tokens & cookies
  • JWT / OAuth 2.0 tokens
  • Multi-factor authentication (MFA)
  • Biometric verification

✅ Verifies identity — establishes who the user is

🛡️ Authorization (AuthZ) WHAT can you do?

"Check your permissions"

  • Can you view this specific record?
  • Can you edit this specific file?
  • Can you delete this specific resource?
  • Are you the owner of this object?
  • Do you have the required role/permission?

❌ IDOR happens when this step is completely missing

⚠️ UUIDs Do NOT Fix IDOR!

Using UUIDs makes IDs harder to guess, but if a UUID leaks through URLs, emails, logs, API list responses, or referrer headers, the IDOR is fully exploitable. Server-side authorization checks are the ONLY real fix. UUIDs are defense-in-depth, not a solution.

🔀 Types of IDOR Vulnerabilities

Classification

By Direction (Who's Affected?)

↔️ Horizontal IDOR Most Common

Same privilege level. User A (regular user) accesses User B's (regular user) data. Both users have identical roles.

# Alice (employee) → reads Bob's (employee) profile
GET /api/users/1002/profile
Authorization: Bearer alice_session_token
# Returns Bob's SSN, salary, medical data!

↕️ Vertical IDOR Privilege Escalation

Different privilege level. Regular user accesses admin-level resources or elevates their own permissions.

# Regular user → accesses admin endpoints
GET /api/admin/users/all
Authorization: Bearer regular_user_token
# Returns ALL users' data including admin secrets!

By Operation (What Can the Attacker Do?)

👁️ Read (GET)

View another user's private data — profile, orders, messages, documents.

GET/api/users/1002/profile
Information Disclosure

✏️ Write (PUT/PATCH)

Modify another user's data — change email, role, settings, password.

PUT/api/users/1002/email
Data Modification

🗑️ Delete (DELETE)

Remove another user's resources — messages, files, accounts.

DELETE/api/users/1002
Data Destruction

➕ Create (POST)

Create resources in another user's context — inject content into their account.

POST/api/users/1002/notes
Context Injection

By Parameter Location (Where's the ID?)

The object ID is embedded directly in the URL path. Most common and easiest to spot. Simply change the number in the URL bar or intercept with Burp Suite.

GET /api/users/1001/profile → Your profile
GET /api/users/1002/profile → Bob's profile (IDOR!)
GET /api/users/1003/profile → Charlie's profile (IDOR!)
GET /api/users/1004/profile → Diana's profile (IDOR!)
GET /api/users/1005/profile → Admin's profile (IDOR!)

ID passed as a query string. Common in search endpoints, filters, exports, and legacy applications.

GET /api/profile?userId=1002
GET /download?fileId=8829
GET /api/export?user=1002&format=csv

ID inside POST/PUT request body (JSON, form data, XML). Harder to spot without intercepting traffic.

POST /api/transfer
{"from_account": "1002", "to_account": "9999", "amount": 5000}
// Attacker changes from_account to victim's ID!

Custom headers carrying user identifiers. Common in microservice architectures where API gateways pass user context via headers.

Object references stored in cookies. Trivially manipulated with browser dev tools, cookie editors, or Burp Suite.

🧪 Lab 1: Horizontal Profile IDOR

Login as one user and attempt to view another user's full profile — including SSN, salary, passport, medical conditions, and bank details.

Vulnerable Read-Based Horizontal

📋 Scenario

TechCorp's internal HR portal lets employees view their own profiles via GET /api/v1/users/{id}/profile. The endpoint checks authentication (valid session token) but does NOT check whether the logged-in user owns the requested profile. An attacker can simply change the user ID in the URL to access anyone's sensitive data.

👩 Alice Logs In

Alice (employee, ID: 1001) authenticates and gets session token. Server knows WHO she is.

2

🔀 Changes ID to 1002

Alice modifies the URL from /users/1001 to /users/1002. Same privilege level — both are employees.

3

💥 Bob's Data Leaked

Server returns Bob's SSN, salary, medical info, bank details — without checking if Alice owns profile 1002.

🧪 Lab 2: Vertical IDOR — Accessing Admin Endpoints

A regular employee attempts to access admin-only API endpoints — system config, all user data, audit logs, revenue figures, and password reset functionality.

Critical Vertical Privilege Escalation

📋 Scenario

  • /api/v1/admin/analytics/revenue — Company-wide financial data

⚠️ Why Vertical IDOR is Often More Dangerous

While horizontal IDOR leaks one user's data at a time, vertical IDOR gives an attacker admin-level access — meaning they can access ALL users' data, modify system configuration, reset any password, and potentially take over the entire application. The /admin/system-config endpoint above leaks database passwords and AWS keys — this is a full system compromise.

🧪 Lab 7: Secure vs Insecure — Side-by-Side

See exactly how the same request behaves with and without proper authorization checks. Toggle between vulnerable and secure server code.

Educational Compare Best Practice

📋 Scenario

This lab lets you toggle between two server implementations of the same endpoint:

  • Insecure — Server uses db.query(User).get(user_id) with NO ownership check. Returns ALL fields including SSN and salary.
  • Secure — Server verifies session.user_id == requested_id, removes sensitive fields, and returns 403 for unauthorized access.
❌ Insecure CodeVulnerable
@app.route('/api/v1/users/<int:uid>/profile')
@login_required
def get_profile(uid):
    # ❌ No ownership check!
    user = db.query(User).get(uid)
    return jsonify(user.to_dict())
    # Returns ALL fields including SSN, salary
✅ Secure CodeFixed
@app.route('/api/v1/users/<int:uid>/profile')
@login_required
def get_profile(uid):
    # ✅ Check ownership!
    if session['user_id'] != uid \
       and session['role'] != 'admin':
        return jsonify({'error':'Forbidden'}), 403
    user = db.query(User).get(uid)
    return jsonify(user.to_safe_dict())
    # Returns ONLY non-sensitive fields

⚠️ Why Mass Enumeration is Devastating

In a real attack, an attacker loops through millions of IDs in minutes using parallel requests, extracting every user's SSN, salary, medical records, private messages, and credentials. POST /reset-password with stolen token

5

💀 Takeover!

Login as Bob with new password

🔗 Chain Logic

Step 1 leaks the email → Step 2 uses that email to trigger a reset → Step 3 steals the token via another IDOR → Step 4 uses the token to change the password → Step 5 logs in with the new password. Each step alone is a vulnerability; together they achieve full account takeover (CVSS 9.8).

📡 Click through each step above to watch the complete account takeover chain unfold!

🔴 This is How Real Account Takeovers Happen

This exact pattern has been reported in hundreds of bug bounty programs. A single IDOR that leaks an email address can cascade into full account takeover when combined with other weak endpoints. This is why every endpoint needs authorization checks — not just the ones you think are "sensitive". CVSS for this chain: 9.8 (Critical).

🛡️ Prevention & Mitigation

Defense

The Golden Rule of IDOR Prevention

NEVER trust user input for authorization decisions. ALWAYS verify on the server side that the authenticated user is authorized to access, modify, or delete the specific requested resource — on every single request.

Fix 1: Server-Side Authorization Checks (Primary Fix)

The most important fix. Every endpoint that handles a resource MUST verify ownership before processing.

❌ Vulnerable (Before)No Check
# ❌ VULNERABLE
@app.route('/api/users/<int:uid>/profile')
@login_required
def get_profile(uid):
    user = db.query(User).get(uid)
    return jsonify({
        'ssn': user.ssn,       # 🔴 Leaked!
        'salary': user.salary  # 🔴 Leaked!
    })
✅ Secure (After)Ownership Check
# ✅ SECURE
@app.route('/api/users/<int:uid>/profile')
@login_required
def get_profile(uid):
    if session['user_id'] != uid \
       and session['role'] != 'admin':
        return jsonify({'error':'Forbidden'}), 403
    user = db.query(User).get(uid)
    return jsonify(user.to_safe_dict())

Fix 2: Scope Database Queries to Current User

❌ VulnerableNo Scope
// ❌ Returns ANY order
db.query('SELECT * FROM orders WHERE id = ?',
  [orderId]);
✅ SecureUser Scoped
// ✅ Only returns user's own orders
db.query(
  'SELECT * FROM orders WHERE id=? AND user_id=?',
  [orderId, req.user.id]);

Fix 3: Session-Based Queries (Eliminate User Input)

# ✅ BEST PRACTICE: No user-controlled ID needed!
@app.route('/api/my-profile')
@login_required
def get_my_profile():
    user_id = session['user_id']  # From SERVER session
    user = db.query(User).get(user_id)
    return jsonify(user.to_safe_dict())

# Instead of: GET /api/users/1002/profile  ← attackable!
# Use:        GET /api/my-profile           ← safe!

Fix 4: Indirect Object References

# Map random per-user tokens to real IDs
# Instead of: GET /api/orders/5001        ← real DB ID
# Use:        GET /api/orders/a8Kx9mPq2wL ← random token

# Token "a8Kx9mPq2wL" maps to order 5001 ONLY for User A
# If User B uses same token → resolves to NOTHING

import secrets
class IndirectRefMap:
    def __init__(self):
        self.maps = {}
    def create(self, user_id, real_id):
        token = secrets.token_urlsafe(12)
        self.maps.setdefault(user_id, {})[token] = real_id
        return token
    def resolve(self, user_id, token):
        return self.maps.get(user_id, {}).get(token)

Fix 5: Reusable Authorization Middleware

# ✅ Reusable decorator — apply to ANY endpoint
def owns_resource(model, id_param='id', owner_field='user_id'):
    def decorator(f):
        @wraps(f)
        def wrapped(*args, **kwargs):
            rid = kwargs.get(id_param)
            resource = db.query(model).get(rid)
            if not resource:
                return jsonify({'error':'Not found'}), 404
            if getattr(resource, owner_field) != session['user_id']:
                if session.get('role') != 'admin':
                    return jsonify({'error':'Forbidden'}), 403
            kwargs['resource'] = resource
            return f(*args, **kwargs)
        return wrapped
    return decorator

# Usage — clean, consistent!
@app.route('/api/orders/<int:id>')
@login_required
@owns_resource(Order)
def get_order(id, resource=None):
    return jsonify(resource.to_dict())

Fix 6: Database-Level Row Security

-- PostgreSQL Row Level Security
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY user_orders ON orders
    FOR ALL
    USING (user_id = current_setting('app.current_user_id')::int);

-- Even buggy app code can't bypass this!
-- DB silently returns ZERO unauthorized rows 🛡️

class OrderViewSet(viewsets.ModelViewSet):
    def get_queryset(self):
        return Order.objects.filter(user=self.request.user)
    # GET /api/orders/5003 → auto 404 if not yours!
class OrderPolicy {
    public function view(User $user, Order $order) {
        return $user->id === $order->user_id;

}
// Controller: $this->authorize('view', $order);
@GetMapping("/orders/{id}")
@PreAuthorize("@orderSec.isOwner(authentication, #id)")
public Order getOrder(@PathVariable Long id) {
    return orderRepository.findById(id).orElseThrow();
}
async function ownsOrder(req, res, next) {
  const order = await Order.findById(req.params.id);
  if (!order) return res.status(404).json({error:'Not found'});
  if (order.userId !== req.user.id && req.user.role !== 'admin')
    return res.status(403).json({error:'Forbidden'});
  req.resource = order; next();
}
