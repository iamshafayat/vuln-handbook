01 📊

Why WordPress Gets Attacked

Market Share

Massive Target Surface

WordPress powers over 43% of all websites. Attackers write one exploit and target millions of sites automatically.

Ecosystem Risk

60,000+ Plugins

Anyone can publish plugins. Code quality varies widely. Vulnerable plugins/themes are the #1 entry point for attackers.

User Behavior

Default Configs Left Unchanged

Most sites ship with predictable usernames, login URLs, and debug settings. Bots scan for these automatically 24/7.

💡
Security Mindset: The goal is NOT "100% secure" — it doesn't exist. The goal is to make your site harder to attack than the next one. Attackers move on when resistance is high. Defense in Depth means multiple layers — if one fails, the next catches it.
02 💀

Attack Types & Vulnerabilities

CRITICAL
🔑 Brute Force Attack
Automated password guessing against wp-login.php
▾

How It Works

Automated bots send thousands of username/password combinations per minute against /wp-login.php. Since WordPress has no native rate limiting, the default install allows unlimited attempts. Botnets use leaked credential lists from breached databases (HaveIBeenPwned).

Real Attack Scenario

A bot finds your site, detects it's WordPress (via /wp-content/ paths), checks /?author=1 to get username "admin", then launches a dictionary attack using the RockYou wordlist (14M+ passwords). Login in minutes if password is weak.

⚠ Real-World Proof & CVE References

→ Sucuri: The WordPress Brute Force Attack Timeline → Wordfence: Large-Scale Brute Force Report 2023 → HaveIBeenPwned — Check if credentials are leaked

✓ How to Fix / Prevent

Change login URL from /wp-login.php to a custom slug (WPS Hide Login plugin)
Limit login attempts to 3–5 (Limit Login Attempts Reloaded plugin)
Enable Two-Factor Authentication (WP 2FA plugin)
Never use "admin" as username — check /?author=1 to verify
Add CAPTCHA to login form (Cloudflare Turnstile is free)
IP whitelist wp-admin via .htaccess if accessing from fixed IP
.htaccess — Block xmlrpc.php & Limit wp-admin Access
# Block xmlrpc.php entirely <Files xmlrpc.php> Order Deny,Allow Deny from all </Files> # Restrict wp-login.php to your IP <Files wp-login.php> Order Deny,Allow Deny from all Allow from YOUR.IP.ADDRESS.HERE </Files>
CRITICAL
💉 SQL Injection (SQLi)
Malicious SQL in forms/URLs to read or modify your database
▾

How It Works

When user input is passed directly into a database query without sanitization, an attacker injects SQL code. For example, a search field accepting ' OR 1=1 -- could dump the entire users table including password hashes.

Impact

Attacker can: extract all users & passwords, read wp_options (site config), create new admin accounts, delete data, potentially read server files via LOAD_FILE(), and write PHP shells via INTO OUTFILE.

⚠ CVE Proof — Real Vulnerabilities

→ CVE-2023-6553 — Backup Migration Plugin SQLi (50K+ sites) → WPScan: WooCommerce SQLi Vulnerabilities → NVD: All WordPress SQLi CVEs (NIST)

✓ How to Fix / Prevent

Always use $wpdb->prepare() for database queries
Use sanitize_text_field() and intval() on all user input
Keep all plugins/themes updated — most SQLi come from third-party code
Use a WAF (Wordfence or Cloudflare) to block SQLi patterns
Change database table prefix from default wp_
PHP — Vulnerable vs Safe Code
// ❌ VULNERABLE — NEVER DO THIS $id = $_GET['id']; $result = $wpdb->query("SELECT * FROM wp_posts WHERE ID = $id"); // ✅ SAFE — Use $wpdb->prepare() $id = intval( $_GET['id'] ); $result = $wpdb->get_row( $wpdb->prepare( "SELECT * FROM wp_posts WHERE ID = %d", $id ) );
CRITICAL
🕷️ Cross-Site Scripting (XSS)
Injecting JavaScript that runs in victims' browsers
▾

Types of XSS

Stored XSS: Script saved in DB (comments, posts) — executes for every visitor.
Reflected XSS: Script in URL parameter, sent back in response.
DOM XSS: Client-side JavaScript reads attacker-controlled data.

Impact

Steal admin session cookies, redirect users to phishing pages, inject crypto miners, deface site, capture keystrokes (password stealing), install malware on visitor machines, create fake admin accounts.

⚠ CVE Proof — Real Vulnerabilities

→ CVE-2023-1119 — WPBakery Page Builder XSS (600K+ sites) → Wordfence: Elementor XSS affecting 1M+ sites (2023) → NVD: All WordPress XSS CVEs

✓ How to Fix / Prevent

Always escape output: esc_html(), esc_attr(), esc_url()
Sanitize input: sanitize_text_field(), wp_kses_post()
Set Content-Security-Policy HTTP header
Use HttpOnly and Secure flags on cookies
Enable Wordfence XSS protection rules
PHP — WordPress Escaping Functions
// ❌ VULNERABLE echo $_GET['search']; // ✅ SAFE — escape before output echo esc_html( $_GET['search'] ); // for HTML content echo esc_attr( $value ); // for HTML attributes echo esc_url( $url ); // for URLs echo wp_kses_post( $content ); // for rich HTML
HIGH
📡 XML-RPC Exploit
Using xmlrpc.php for amplified brute force & DDoS
▾

How It Works

WordPress's xmlrpc.php allows bulk login attempts via the system.multicall method — 100+ username/password combinations in a single HTTP request. This bypasses most rate-limiting protections and amplifies brute force attacks 100x.

Impact

Brute force at scale (100 attempts per request), DDoS amplification (pingback.ping method), content posting without proper auth, server resource exhaustion. Often used in botnets targeting WordPress installations.

⚠ Proof & References

→ Sucuri: XML-RPC Brute Force Amplification Attack → Acunetix: WordPress Pingback DDoS via XML-RPC

✓ How to Fix / Prevent

Disable xmlrpc.php completely if not needed (Wordfence can do this)
Use .htaccess to block access to xmlrpc.php (code above)
If Jetpack is used, selectively allow only Jetpack IPs
Use "Disable XML-RPC" plugin for a one-click solution
HIGH
📁 File Inclusion (LFI / RFI)
Reading server files or executing remote code via vulnerable plugins
▾

LFI (Local File Inclusion)

Attacker manipulates a file path parameter to read sensitive files: /etc/passwd, wp-config.php, log files. Can lead to credential theft or further exploitation.

RFI (Remote File Inclusion)

When allow_url_include is enabled, attacker includes a remote PHP file hosted on their server. This executes arbitrary code on your server — full compromise. PHP shell uploaded, site owned.

⚠ CVE Proof

→ CVE-2022-1386 — Fusion Builder LFI (100K+ sites) → NVD: WordPress File Inclusion CVEs

✓ How to Fix / Prevent

Set allow_url_include = Off and allow_url_fopen = Off in php.ini
Keep all plugins and themes updated
Validate and sanitize all file path inputs in custom code
Use a WAF (Wordfence) to detect LFI/RFI patterns in requests
CRITICAL
🦠 Malware & Backdoor Injection
Hidden PHP shells in nulled themes/plugins — #1 cause of WP hacks
▾

How It Happens

Nulled (pirated) themes/plugins contain hidden PHP code. When installed, it creates backdoor files, sends credentials to attacker's server, injects spam links into your content, runs SEO spam, and maintains persistent access even after password changes.

Common Malware Types

Backdoors: Allow re-entry after cleanup.
SEO Spam: Inject hidden casino/pharma links.
Redirects: Send visitors to malware sites.
Cryptominers: Use visitor CPU for crypto.
Phishing pages: Fake login pages on your domain.

⚠ Proof & Stats

→ WordPress Plugin Hack 2026 → Wordfence: Malware Found in Nulled Plugins Research

✓ How to Fix / Prevent

NEVER install nulled/cracked themes or plugins — ever
Buy from official sources: wordpress.org or ThemeForest/CodeCanyon
Scan every plugin zip with VirusTotal before installing
Run weekly malware scans with Wordfence or Sucuri
Monitor file changes — Wordfence alerts on new/modified files
If hacked: restore from backup, scan, change ALL passwords, update everything
HIGH
⬆️ Privilege Escalation
From Subscriber to Admin without credentials
▾

How It Works

A logged-in user with low privileges (Subscriber) exploits a broken access control flaw in a plugin to modify their own role to Administrator. Common with plugins that allow profile updates without proper capability checks.

IDOR Example

Plugin has an endpoint admin-ajax.php?action=update_profile&role=administrator with no server-side permission check. Any logged-in user can POST this to make themselves admin. This is called IDOR (Insecure Direct Object Reference).

⚠ CVE Proof

→ CVE-2021-34621 — ProfilePress Privilege Escalation (400K sites) → Wordfence: ProfilePress Priv Escalation Deep Dive

✓ How to Fix / Prevent

Always check capabilities before sensitive actions: current_user_can('manage_options')
Use check_ajax_referer() in all AJAX handlers
Never allow user-supplied role changes without strict server-side validation
Keep all plugins updated — priv escalation patches release frequently
Audit user roles regularly — remove unnecessary admin accounts
MEDIUM
🎭 CSRF (Cross-Site Request Forgery)
Tricking an admin into executing malicious actions
▾

How It Works

Attacker sends an admin a link that, when clicked, automatically performs an action (delete user, change settings, create post) using the admin's existing authenticated session. No credentials needed.

WordPress Defense: Nonces

WordPress uses nonces — time-limited tokens embedded in forms and URLs. Every sensitive action should verify a nonce. Without it, any external site can forge requests on behalf of authenticated users.

⚠ References

→ OWASP: CSRF Attack Explained → WordPress Developer Docs: Using Nonces

✓ How to Fix / Prevent

Generate nonces: wp_create_nonce('my_action')
Verify nonces: check_admin_referer('my_action') or check_ajax_referer()
Include nonce field in all forms: wp_nonce_field('my_action', '_wpnonce')
PHP — WordPress Nonce Implementation
// In your form <form method="post"> <?php wp_nonce_field( 'delete_post_action', '_wpnonce' ); ?> <button type="submit">Delete</button> </form> // In your handler — verify before doing anything if ( ! check_admin_referer( 'delete_post_action', '_wpnonce' ) ) { wp_die( 'Security check failed.' ); }
MEDIUM
🔓 Sensitive Data Exposure
Leaking credentials, debug info, and config files publicly
▾

Common Exposure Points

• wp-config.php readable from browser
• /wp-content/debug.log publicly accessible
• .env file exposed
• Directory listing enabled (see all files)
• WordPress version in meta tags
• User enumeration via /?author=1

What Attackers Get

Database hostname, name, username, and password from wp-config.php. API keys from .env. PHP errors with file paths from debug.log. Username discovery from author archives. All of this enables targeted, high-success attacks.

⚠ References

→ OWASP Top 10 — A02: Cryptographic Failures & Data Exposure

✓ How to Fix / Prevent

Move wp-config.php one level above webroot (WordPress supports this)
Set file permissions: chmod 400 wp-config.php
Set WP_DEBUG to false and WP_DEBUG_LOG to false in production
Disable directory browsing: add Options -Indexes to .htaccess
Remove WP version from header: add to functions.php: remove_action('wp_head', 'wp_generator')
Block /?author= enumeration via Wordfence or .htaccess

Security Hardening

Login Security

🔐 Securing the Login System

  • ✓Change login URL using WPS Hide Login plugin — /wp-login.php gets thousands of bot hits dailyMUST
  • ✓Enable Two-Factor Authentication (2FA) for all admin and editor accountsMUST
  • ✓Install "Limit Login Attempts Reloaded" — lock out after 3–5 failed attemptsMUST
  • ✓Never use admin as username — verify by visiting /?author=1 on your siteMUST
  • ✓Use a password manager to generate 20+ char unique passwords for admin accountsHIGH
  • ✓Add Cloudflare Turnstile CAPTCHA (free) to login formHIGH
  • ✓If on fixed IP — whitelist your IP for wp-admin access via .htaccessMEDIUM
Server & File Security

🖥️ File Permissions & Server Settings

  • ✓Set wp-config.php permission to 400 or 440 — no world-readable accessMUST
  • ✓Folders: 755, Files: 644, wp-config.php: 400MUST
  • ✓Disable directory listing with Options -Indexes in .htaccessMUST
  • ✓Disable xmlrpc.php if not using Jetpack or WP mobile appMUST
  • ✓Set PHP display_errors = Off and log_errors = On in productionHIGH
  • ✓Keep PHP version updated — use PHP 8.1+ minimum. PHP 7.x is end-of-lifeHIGH
  • ✓Enable HTTPS/SSL everywhere — force redirect HTTP → HTTPSMUST

.htaccess — Complete Security Rules
# ══════════════════════════════════ # WORDPRESS SECURITY .HTACCESS RULES # ══════════════════════════════════ # 1. Disable directory browsing Options -Indexes # 2. Block access to sensitive files <FilesMatch "^(wp-config\.php|\.env|debug\.log|readme\.html|license\.txt|xmlrpc\.php)$"> Order Allow,Deny Deny from all </FilesMatch> # 3. Block access to .htaccess itself <Files .htaccess> Order Allow,Deny Deny from all </Files> # 4. Prevent PHP execution in uploads folder <Directory "/var/www/html/wp-content/uploads"> <FilesMatch "\.php$"> Order Deny,Allow Deny from all </FilesMatch> </Directory> # 5. Block author enumeration /?author=N RewriteEngine On RewriteCond %{QUERY_STRING} ^author=\d RewriteRule ^ /? [L,R=301] # 6. Block common attack patterns in query strings RewriteCond %{QUERY_STRING} (base64_encode|union|select|insert|drop|update|benchmark) [NC] RewriteRule .* - [F]
